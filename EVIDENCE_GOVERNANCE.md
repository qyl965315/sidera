# Evidence governance

Canonical source: `core/evidence-governance.ts`. The provider-neutral PolicyEvidenceRegistry owns exact policy subjects. Adapters cannot supply or change their policy grade through onboarding or Gateway status. Human product configuration, Node authority, runtime presence and provider documentation remain separate facts. Model consensus is never proof or provider approval.

The static Gateway edge contract now exposes `interfaceSupport`, not `status`. `IMPLEMENTED` describes repository implementation only. Gateway `health` is retained as a runtime compatibility field and remains UNKNOWN without correlated evidence. `runtimeConnectivity` and the four-dimensional `support` projection are returned by Gateway status and Desktop onboarding. No static CONNECTED or READY_FOR_IMPORT status remains in the edge model. Consumers of the old edge status must migrate to interfaceSupport and support.runtime.

A support subject comprises provider, product, interface, executionMode, authMode, entitlement, accountType and deployment. Every field must match. Official Codex client login does not imply third-party app-server orchestration; Gemini CLI does not imply Antigravity; ZCode application authorization does not imply zcode-native-service. Generic compatible APIs and unspecified external MCP subjects stay unknown. Grok Chat MCP ingress does not imply model execution access.

Policy source types and states are independent. Types include implementation_test, protocol_test, runtime_observation, official_document, provider_terms and human_attestation; states include current, stale, superseded, conflicted and unavailable. Official documents and terms seed the policy registry; runtime observations never rewrite policy. Conflicting same-scope records or conflicted sources produce conflicted. Unavailable/superseded/stale sources cannot support a current conclusion.

The initial claims come from the supervising GPT review supplied in the Human brief on 2026-10-07. No remote page bytes were retrieved by this implementation. sourceHash hashes the canonical local JSON claim bundle `{exactScope, claims, limits}` and hashKind is canonical_claim_bundle_sha256. Source retrievedAt records the supplied review date, not an independent network fetch by this run. checkedBy describes this provenance. The JSON artifact is generated from the canonical TS registry; it is not a second editable source.

Freshness is calculated from checkedAt and nextReviewAt at the supplied clock. Missing exact-scope evidence is NO_EVIDENCE, which is intentionally distinct from an existing but expired STALE record. The deadline is exclusive, invalid timestamps and future observations fail closed. Provider evidence expires after 30 days; the OpenAI Sign in with ChatGPT subject expires after 14 days. Source states are projected stale when the review window expires. No hand-authored fresh flag exists.

Runtime observations require exactScope, observedAt, expiresAt, evidenceRef and a request/response correlation. Missing, unqualified or wrong-scope observations produce UNKNOWN with NO_EVIDENCE freshness; a qualified observation past expiresAt produces UNKNOWN with STALE freshness. Configured sessions, installed executables, help output and local login reports cannot become OBSERVED_CONNECTED. A grant requires an exact subject scope and evidence reference; absent authority remains unknown. This projection describes evidence and does not issue permissions or replace Core enforcement.

SUPPORTED requires IMPLEMENTED, implementation test references, a current correlated connection, evidenced exact-scope grant and current documented policy. Documented limitations produce SUPPORTED_WITH_LIMITS. Unknown/stale/conflicted policy or machine mismatches block with NEEDS_REVIEW. Denied authority/offline runtime yields UNAVAILABLE; explicitly unsupported implementation/policy yields UNSUPPORTED. Every blocking dimension is included in machine-readable blockers.

Desktop onboarding preserves separate configured state, detector installation/contract state and configured executable existence. Configured versus missing installation, unavailable detector contract or missing configured executable creates an explicit machine conflict. Runtime/detector disagreement is also separate from policy. Details expose host kind, not raw adapter options. Integration details and Settings Advanced disclose the four dimensions, source URLs, freshness, scope and blockers without an execution console.

## Deterministic documents

Run `npm run evidence:generate` to regenerate SERVICE_ONBOARDING_MAP.md, MCP_COMPATIBILITY.md, evidence/policy-evidence-registry.json and evidence/docs-fixture-snapshot.json. Run `npm run evidence:check` to detect drift. The fixed snapshot is 2026-10-07 and explicitly labeled a fixture, not this machine. Live Desktop onboarding uses the existing bounded read-only detector and config projection; the generator does not read credentials, runtime specs or Gateway config. Both documents mark GENERATED / DO NOT EDIT, include generatedAt and freshness, and state that runtime observations expire. Old generated documents are not canonical.

## Operational limits

No real provider login, model invocation, connection import, session replacement, authority grant, packaging, release or GitHub publication is part of validation. The existing Chief binding and Gateway/Core data are not modified. Current Gateway/Host observations and Core grants are not imported into this registry in this pass: their runtime and authority dimensions remain unknown until a trusted correlated observation/evidenced grant is supplied. The projection does not fabricate a current machine snapshot or endorse Sidera participation in Sign in with ChatGPT.
